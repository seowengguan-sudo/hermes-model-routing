# Hermes Runtime Introspection

## When to use
- User asks how the real/current/default Hermes agent works (intake, processing loop, tools, context, memory, skills, MCP, model selection, free-tier limits).
- User asks where something lives on disk, or how a mechanism is actually implemented.
- Any "how does Hermes X" question where a verified, source-grounded answer beats a recollection or a design-doc citation.

## Core rule (user preference — explicit and repeated this session)
**Explain the ACTUAL current agent, not the designed/not-yet-implemented architecture.** The user firmly scoped this: when asking "how does Hermes work," they mean the default runtime as it runs today (single LLM + tool layer + session + persistent memory + skills), NOT the multi-agent / cost-router / interrupt-poller designs documented elsewhere. Only mix in designed material if the user explicitly asks. Verified facts come from reading source/config, never from proposal docs.

## The technique (how to answer)
1. **Don't guess or cite design docs. Inspect the real install.**
   - Running config: `HERMES_HOME` (default `/opt/data`) -> config at `$HERMES_HOME/config.yaml`. NOTE: `/opt/hermes/config.yaml` may NOT exist; the active config is under HERMES_HOME.
   - Skills: scan BOTH `/opt/hermes/skills` (bundled, ~71) AND `$HERMES_HOME/skills` (profile dir, ~85, includes `.hub/`). UI "total" = deduped union minus disabled. `HERMES_HOME` resolves via env or `_skills_dir()` in `tools/skills_tool.py`; `_find_all_skills()` merges both.
   - MCP: catalog entries are `manifest.yaml` files under `/opt/hermes/optional-mcps/<name>/` (6 shipped: blender, comfy-cloud, figma, linear, n8n, unreal-engine). Client/server code: `tools/mcp_tool.py`, `mcp_serve.py`, `hermes_cli/mcp_catalog.py`, `hermes_cli/mcp_config.py`.
   - Model context lengths: `agent/model_metadata.py` `_CONTEXT_LENGTHS` dict (e.g. `hy3`: 262144). Free-tier catalog: `hermes_cli/models.py` (search entries tagged `:free`).
   - Tool invocation: native tools in `tools/*` (terminal_tool, file_tools, file_operations, web_tools). `execute_code` hermes_tools stubs generated by `tools/code_execution_tool.py` from `SANDBOX_ALLOWED_TOOLS` (web_search, web_extract, read_file, write_file, search_files, patch, terminal) + helpers `json_parse`/`shell_quote`/`retry`. Limits: 300s, 50 calls, 50KB stdout.
   - `write_file` syntax gate: `tools/file_operations.py` `LINTERS` (`.py`->`python -m py_compile`); only NEW errors surfaced; `.json/.yaml/.toml` parsed in-process; returns `verified:true`.
2. Read the actual file, quote the real path/line, then explain in plain language with a worked example.
3. Be honest about limits: if you can't see runtime internals (e.g. exact compaction threshold), say so; show the evidence you DO have (e.g. the `[CONTEXT COMPACTION]` block at the top of context).
4. Separate what's LOCAL (runs in the user's container) from what goes to the MODEL PROVIDER (only call/result text in the prompt).

## User communication preference (for this class)
User wants DEEP, STEP-BY-STEP, EXAMPLE-RICH explanations: numbered steps, labeled parties (You / Runtime / Model), real file paths, and concrete worked prompts. Avoid thin summaries. When a figure (RPM/TPM/context) isn't verified, say so and show the conflict rather than asserting.

## Pitfalls
- Don't claim a model/feature is "broken" or "unavailable" from a transient session failure — verify against source. A 404 on vision does NOT mean the model is dead (see `references/vision-404-vs-dead-model.md`).
- Don't build repetitive daily automation. Each run must be gap-aware & incremental — read prior notes/SUMMARY, emit only what is genuinely NEW, else skip. See `references/incremental-vs-repetitive-cron.md`.
- Don't invent API keys, paths, or numbers. If unverified, flag it.
- MCP != native tools. Native tools (terminal, read_file) are direct runtime calls; MCP is the bridge for EXTERNAL tool servers (catalog) and cross-AI interop (server mode). The "6 MCP not installed" = optional catalog, not required.
- Installing an MCP does NOT bill the external service from your model tokens; it adds tool-schema tokens to every context turn (model-side only) + result tokens. Local MCPs (blender/unreal) cost $0 external.
- Free-tier availability is catalog-gated: `laguna-s` (1.05M ctx) is NOT in the free catalog; only `laguna-m.1:free` is. Verify against `hermes_cli/models.py` before recommending a model as "free."

## Session Loss / State DB Recovery (learned this session)
If the user reports ALL sessions vanished from the Hermes dashboard:
1. Check `/opt/data/state.db` — if it has a valid SQLite header but the `sessions` table returns 0 rows, the DB was zeroed (not deleted). Docker daemon NOT running = not the cause.
2. Check `/opt/data/state.db-wal` — if it exists on disk and has nonzero size, it contains recent writes. If it was consumed/nothing on disk, check git: `git log --oneline --diff-filter=A -- state.db` to find the commit that captured the WAL.
3. **Recovery technique:** `git show <commit>:state.db-wal > /tmp/recovery-wal` extracts the WAL from git history. Parse B-tree leaf pages manually (SQLite CLI may not be installed — use python3). WAL page1 header gives database page count; frame headers give page numbers.
4. **Key finding from this recovery:** WAL pages contain session records as SQLite B-tree leaf cells (type 0x0D). Session IDs match pattern `(20YYMMDD_HHMMSS_6hex)` or `cron_<hex>_<date>_<time>`. Model config JSON (`{"model": ..., "provider": ...}`) is stored inline at the start of each session's payload. System prompt (~3,749 chars) is embedded in every session record. Overflow pages (when payload > page_size) must be followed via SQLite overflow page chaining.
5. **Files to restore from git after state.db loss:** The skills/, knowledge/, workspace/, cron/, docs/ directories are tracked in git commit 54c4651. If they're missing from the working tree (deleted by a botched git checkout), restore with: `git checkout 54c4651 -- skills/ knowledge/ workspace/ cron/ docs/`. The `.gitignore` in commit 450adc2 excluded `state.db*` which is why the DB itself was never tracked — only the WAL was accidentally committed.

See `references/state-db-recovery.md`.
