## Run 4 (Eve) — Evals: prove the tool is right BEFORE you trust it

Run 3's teaser was "how do you *prove* the tool/agent is right before you trust it." Here's the answer in business terms.

- **Eval = a fixed acceptance test for your AI.** A spreadsheet of real past cases where you *already know the correct answer*; you run your tool/agent over them and count how often it's right. Same idea as a factory QA check on a production line before parts ship — you don't ship on vibes.
- **Why it exists:** an AI that *sounds* confident is not an AI that *is* correct. Without an eval you can't tell if a change helped or hurt, and you can't defend the demo to the Director when he asks "how do you know it's right?"
- **PENSOLAR example:** take 20 closed projects; the "known answer" for each is its real permit status, its real awarded vendor quote, its real install date. Run `get_permit_status` across all 20 and score % correct → that's your baseline accuracy.
- **Two cheap eval types to start:** (1) *output eval* — does the answer match the known value? (2) *guardrail eval* — on a high-risk action, does it correctly STOP for human approval? Both reuse the same project data as the test set, so no new data plumbing.
- **Ties back to earlier lessons:** evals are what let you safely RAISE the autonomy dial — you only promote a tool from "suggest" (dial 0) to "act" (dial 10) *after* it passes its eval. And evals decide tool-use vs agentic: if a one-shot tool scores 95% on the set, don't build the loop.
- **POC takeaway:** ship a tiny eval harness (a CSV of ~20 cases + a 20-line score script) beside the first tool demo. That is the difference between "it seems to work" and "here is the measured accuracy the Director can audit."

## Run 3 (PM) — When a tool call is enough — vs. when to justify an agentic workflow
Definitions are clear; the real POC question is **where to spend**. Two solar-PM scenarios show the line.

- **Tool use** = one well-defined action with known inputs and a predictable output. Example: "What's the permit status for SunnyVilla?" → the model calls `get_permit_status(project_id)` once and answers. You wired the sequence; it just fires the function.
- **Agentic workflow** = a *goal* with an unknown path. Example: "Get SunnyVilla install-ready" → the model must check the permit, chase the authority if pending, pull 3 vendor quotes, compare, pick one, schedule the crew, and reschedule if the permit slips — looping and self-correcting as results return.
- **The tradeoff (Anthropic):** agentic loops cost more money and latency. They only earn it where deterministic rules can't handle the variation. Default to the simpler pattern.
- **Your default:** start PENSOLAR with tool use + simple workflows (prompt chaining / routing). Build a free agent loop only when a real pain proves rules fail.

## Why it matters for your POC
PENSOLAR's pain — slow staff replies, Director blind to exceptions — is *first* a tool-use + routing problem, not an autonomy problem. A tool-use demo is faster to build, cheaper to run, and easier to guardrail, yet still shows the AI win. Pitching a full autonomous agent risks cost, latency, and a runaway mistake before you've proven value.

## Run 5 (Eve, follow-on) — Precision, Recall & the Confusion Matrix: why accuracy lies for rare, high-stakes events

Last lesson gave you evals — a fixed test set + a score. But the score you pick decides whether you ship something *safe* or something that only *looks* safe. Plain accuracy hides the exact failure that matters most in a guardrail.

- **Confusion matrix = the 2×2 that names every kind of mistake.** For any yes/no AI decision: True Positive (right to flag), False Positive (flagged but was fine — a false alarm), False Negative (missed it — should have flagged, didn't), True Negative (right to pass). Accuracy = (TP+TN)/all — but it blends the two mistakes into one number.
- **Precision = of the times you said "block," how many really were.** Low precision = you cry wolf a lot (annoying, usually harmless). Formula: TP/(TP+FP).
- **Recall = of the real risks, how many you caught.** Low recall = you let danger through (the dangerous one). Formula: TP/(TP+FN).
- **Why accuracy lies here:** if only 3 of 20 projects truly needed a block, a tool that *never blocks* scores 17/20 = 85% accuracy — and catches ZERO real risks (recall = 0%). For a safety guardrail, that 85% is a lie that gets a crew booked before the permit clears.
- **PENSOLAR example:** the `auto_schedule_crew` guardrail. The "positive" class = *permit not cleared, must block* — it's rare (maybe 3/20). Score **recall** as the safety gate (want ~100% — never miss a block), and track precision so you know your false-alarm rate (annoying but survivable). Accuracy is the number you show the Director last, not the one you gate on.
- **POC takeaway:** when you build that 20-case eval set, don't stop at one accuracy % — report the 2×2 for every guardrail tool, and write the *recall* cutoff into the spec for any irreversible / high-risk action.

## Run 6 (Late) — The Golden Set: your eval is only as good as its ground truth

You now know evals and you know recall gates safety. But three runs in a row the gap hasn't moved: the 20-case set still isn't built. So today the concept IS the artifact — how to curate ground truth, and the traps that quietly make a "passing" eval worthless.

- **Golden set = the audited answer key, not a data dump.** 20 closed PENSOLAR projects where a human has *signed off* on the correct answer per field. If nobody signed off, you don't have ground truth — you have a second opinion, and your eval measures agreement, not correctness. This is exactly your QA calibration standard: an instrument checked against an uncalibrated reference proves nothing.
- **Label at the decision, not the record.** Don't label "permit status = pending." Label *the decision the tool must make*: "should `auto_schedule_crew` have blocked? YES/NO." An eval must test the output the business acts on, or you'll score 95% on data lookups while the risky decision stays untested.
- **Stratify, don't sample randomly.** Random 20 closed projects will contain ~1 real block case — too few to measure recall at all. Deliberately over-include the rare, ugly, high-stakes cases: expired permit, vendor withdrew a quote, customer changed scope mid-install. A golden set is chosen for *coverage of failure modes*, not to look like the average month.
- **Freeze it, version it, never tune on it.** Save as `golden_v1.csv` and lock it. If you keep editing the set until the tool passes, you've fitted the exam to the student. Standard discipline: split — tune on a dev set, report on the frozen golden set only.
- **Ground truth rots.** Permit rules change, vendors churn, the Director's escalation threshold moves. Re-audit the set quarterly and bump `golden_v2`. A stale answer key means your recall number is measuring last year's business.
- **Minimum viable shape (build this):** `project_id | question_type | input_snapshot | correct_answer | should_block | labeled_by | labeled_date | version`. Eight columns, 20 rows, one CSV. `input_snapshot` matters — freeze the data as it looked at decision time, or the tool "answers" using facts nobody had yet (that's leakage, and it inflates every score you report).
