## Concept — shift the quality gate LEFT: score_eval.py blocks the deploy, not just reports it
- **The recall gate you have lives at RUNTIME (rollout_spec §3 auto-rollback) + in PRODUCTION (drift).** That catches bad behavior AFTER code is live. A developer can merge a change that drops block-case recall 100%→85%, ship to canary, and miss 3 block cases before the runtime gate ever fires. The cheapest catch is BEFORE deploy.
- **Make score_eval.py a CI gate, not a report.** Wire it into the PR/build pipeline: every change to the crew's prompt, tools, or parsing runs score_eval.py vs golden_v1.csv (audited!) and the PR FAILS if recall on block cases < target. The agent never reaches shadow until it passes. Same number that gates rollout now also gates the merge — "shift left."
- **Not a 10th rung — the same metric, one lifecycle stage earlier (commit → CI → deploy → runtime → drift).** R5/R7 taught you the number; cost-axis taught you its $ value; this enforces it at the cheapest point. Defense in depth = runtime gate + pre-deploy gate = two independent catches (bad CODE change vs real-world DRIFT).
- **PENSOLAR failure it prevents:** a dev "improves" the permit-status parser prompt; block-case recall silently 100%→85%. The runtime gate catches it only after canary mis-schedules 3 projects (TNB penalty + 2-wk delay). A CI gate fails the PR in ~4 min — zero live exposure, zero penalty.
- **Cost lens (his mandate):** a pre-deploy catch costs ~4 min of CI + a dev re-write; a post-deploy catch costs 3 mis-scheduled projects + 2-wk TNB delay + rollback investigation. Earlier gate = cheaper miss — the cost-axis lesson applied to the BUILD stage.
- **The dependency it exposes (ties back to the audit):** the CI gate is only as real as golden_v1. If golden_v1 is still EXAMPLE-SYNTH, "recall 100% in CI" is the self-lick again. So audit (hand-off step 1) must land BEFORE the gate means anything. Re-sequences the hand-off: audit → gate → live.
